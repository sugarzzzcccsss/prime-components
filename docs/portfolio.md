# 为多项任务共同选择模块库存

v0.2.0 新增 `portfolio` 命令。任务依次执行，同一模块可以在不同任务中重复使用；不模拟多项任务同时占用模块。

```sh
python -m prime_components portfolio --input examples/portfolio.json --output results/portfolio.json
```

## 研究问题

分别求出每项任务的最优配置，再把所有配置合起来，未必得到最少型号的共同库存。因此程序现在直接检查一个候选库存能否为每项任务提供合格子集。

输入仍是 `modules` 与 `tasks`；具体字段与单任务模型相同。新规划器额外检查同型号的名义能力集合、接口标签和声明功耗一致，避免通过给不同模块贴同一个型号标签制造“少型号”结果。不同实例的 `id` 和健康状态可以不同。这只是输入语义检查，没有认证实际硬件规格。

## 示例的含义

`examples/portfolio.json` 定义两项顺序任务：检查需要两个 `inspect` 能力实例，移动需要一个 `move` 能力实例。专用感知与运动模块各声明 1 W，具有两种能力的共享型号声明 1.5 W；另有一个 5 W 的通用型号会违反任务预算。这些数值均是构造的假设。

| 选择方法 | 共同库存 | 型号数 | 实例数 | 检查任务的功耗和 / 移动任务的功耗和 |
| --- | --- | ---: | ---: | --- |
| 每项任务单独最优后合并 | 两个 vision 实例、一个 motion 实例 | 2 | 3 | 2 W / 1 W |
| 联合选择 | 两个 shared 实例 | 1 | 2 | 3 W / 1.5 W |

这个例子展示减少型号与实例的同时，任务功耗可能上升。它不证明现实中存在这种共享硬件，也不证明这个选择具有最低成本。

## 搜索范围和排序

最多接收 16 个模块和 32 项任务；空任务集被拒绝。仅 `ready` 模块可选。对于每项任务，预先计算每个模块子集是否满足能力数量、接口和功耗约束，再传播到包含该子集的库存。最后按照以下顺序比较可行库存：型号数、实例数、库存声明功耗和、排序后的 ID。

时间复杂度主要为 O(T × N × 2^N)，其中 N 是 ready 模块数，T 是任务数；它是有限规模的精确参考方法。限制规模是为了让穷举保持可复现，后续可以用整数规划等方法与它比较正确性。

`inventory_power_w` 是所选库存的声明功耗之和，只用于排序和对照。每项顺序任务只使用自己的 `task_plans` 子集；库存总和不是实际同时耗电量，也不包含电源效率与瞬态负载。

## 输出和复核

报告包含输入、研究边界、联合库存、每任务计划、排序目标，以及各任务独立优化后形成的库存对照。无解时 `feasible` 为 false，CLI 保存报告并返回 1；非法输入返回 2。

测试用小库存上的直接嵌套枚举作为另一种实现进行比较，并加入型号不一致、不可行、失效、接口、预算和确定性案例。通过测试只支持给定符号约束下的计算正确性。

实际连接、运动学、负载、校准、持续/峰值功率和任务质量仍需要实物数据。本工具不能用于直接选择真实机器人执行动作。
