日期：2026-10-26。记录来自 Windows、Python 3.13.0；原始报告中 `cpu_count` 为操作系统报告的逻辑 CPU 数，不代表专用核心或计算额度。

## 结果

| 检查 | 本地结果 | 能说明什么 |
| --- | --- | --- |
| 完整测试套件 | 31 项通过 | 覆盖规划、参数、CLI、HTTP 协议、故障和清理等软件行为 |
| 三次正常完整实验 | 每次三种场景各 12 个任务，摘要全部匹配 | 单进程基线、多进程正常和多进程故障结果一致 |
| 在途任务恢复 | 进程 0 在计算前门控点退出，原有其余进程完成第二次尝试 | 有真实进程退出和重派，没有新增替代池制造恢复 |
| 无可用工作进程负例 | 停用并终止全部初始进程，报告 failed；预留任务未完成 | 无幸存者时不会误报全部完成，有限结束并保留证据 |

| 清理 | 正常与负例均确认自建工作进程和服务器主线程退出 | 完成后不保留工作进程作为后台服务 |

## 复现和原始记录

```sh
python scripts/record_local_evidence.py --output results/local-evidence
```

已提交的 [记录目录](../benchmarks/runtime-v0.2.0) 包含三次实验 `run-01.json` 至 `run-03.json`、所有进程不可用负例、库存规划、完整测试日志与 `summary.json`。汇总保存 Python 源文件的 SHA-256，按 UTF-8、去 BOM、LF 换行计算，便于跨平台核查。

`workers_claimed` 只代表领取过任务；`workers_completed` 代表至少有一个结果被接受。故障进程属于前者，不属于后者。所有工作进程均在放开任务分配前通过真实 HTTP 完成握手；启动了多少进程不等于每个都分到任务。

三次实验固定场景顺序，使用同一工作负载和同一机器。测时保留在原始报告中，本版不据此声称通用加速比、置信区间、硬件可靠性或能耗收益。

## 审查中修正的关键问题

- 故障场景改为启动完整工作进程池后再注入故障，由既有幸存进程接管。
- 事件增加单调时间和工作进程标签，报告保留任务摘要；领取与完成分别统计。
- 注入计时起点前移到终止请求之前，失败报告和清理结果参与完成判定。
- 全进程失效负例先禁止整个池继续领取或接受结果，消除回收时的抢跑窗口。
- 同型号声明规格必须一致；规划对照覆盖多能力数量、预算、接口、失效、无解与多实例结果。

这些审查意见只是补充，验收依据仍是实际执行结果和记录。
